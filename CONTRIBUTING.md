# Contributing

Небольшой проект, простой процесс — без формального CLA/RFC, но с обязательным зелёным CI.

## Настройка окружения

См. [README.md](./README.md) — раздел «Разработка» (Supabase, переменные окружения, `npm run dev`).

## Перед тем как открыть PR

```bash
npm run typecheck
npm run lint
npm test           # 403 unit/integration-теста, ~10с, без БД
npm run test:e2e   # Playwright — нужен поднятый Supabase (npx supabase start) и dev/prod сервер на :3000
```

`npm run test:e2e` необязателен для каждого PR (нужен реальный Supabase), но обязателен для любых изменений, затрагивающих аутентификацию, читалку, SRS-повторение, App Router routing или сам Next.js — эти пути покрыты Playwright-сценариями, которые всё равно прогонит CI перед мерджем.

## CI

Каждый PR проходит 4 обязательных проверки (см. [`.github/workflows/ci.yml`](./.github/workflows/ci.yml)) — все должны быть зелёными перед мерджем:

- **`checks`** — `tsc --noEmit`, `eslint`, `next build`
- **`npm-audit`** — прямые зависимости на известные CVE
- **`unit-tests`** — `npm test`
- **`e2e`** — полный Playwright-набор на реальном Supabase (`supabase db reset` → build → start → тесты)

## Соглашения

- **Ветки**: `<type>/<short-kebab-slug>`, где `type` — `feat`, `fix`, `docs`, `ci`, `test`, `audit`. Пример: `feat/hybrid-gamification-visuals`.
- **Коммиты**: `<type>: <краткое summary>` (`feat:`, `fix:`, `docs:`, `chore:`, `ci:`) — тело коммита объясняет *почему*, не только *что*, если изменение не самоочевидно.
- **Комментарии в коде**: на русском, объясняют причину решения (почему так, а не «что» — код и так читаем); идентификаторы (переменные, функции, типы) — на английском.
- **RLS прежде всего**: любая новая таблица с пользовательскими данными — сразу с политикой `owner_id = auth.uid()` в той же миграции, не отдельным PR «на потом».
- **Визуальные изменения**: любое изменение, видимое в браузере, — проверяется живьём через dev-сервер (скриншот до/после в PR), не только `tsc`/`lint`.
