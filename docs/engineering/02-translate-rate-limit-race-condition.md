# Race condition в rate-limit перевода — фикс через pg_advisory_xact_lock

**Код:** `supabase/migrations/0045_atomic_translate_rate_limit.sql`, `src/lib/translate-request.ts`
**Проверено живьём:** `e2e/translate-rate-limit-race.spec.ts`
**Контекст:** `docs/release-2026-08-22/02_KRITICHNYE_BAGI_SEYCHAS.md` B.2

## Три поколения одного и того же бага

Лимит — 30 переводов в минуту на пользователя (`translate_requests` — таблица-лог с одной строкой на запрос, `owner_id` + `requested_at`, скользящее окно, не фиксированные бакеты).

**Поколение 1 (исходная реализация).** Сначала считали, потом вставляли:

```
SELECT count(*) WHERE owner_id = X AND requested_at >= now() - interval '60s'
if count <= LIMIT: INSERT
```

Худший случай race: N параллельных запросов одновременно делают `SELECT count`, все видят одно и то же число (ни один ещё не успел вставить свою строку), все проходят проверку, все вставляют. Лимит в 30 не спасает даже от банального double-click или ретрая клиента.

**Поколение 2 (P0-АУДИТ 3.3, 2026-07-23).** Поменяли порядок — сначала вставляем, потом считаем уже вместе со своей новой строкой:

```
INSERT (owner_id)
SELECT count(*) WHERE owner_id = X AND requested_at >= now() - interval '60s'
if count <= LIMIT: allow
```

Это закрывает самый грубый случай (пустая гонка на старте), но собственный комментарий кода честно называл это "не идеально атомарно" — потому что `INSERT` и `SELECT count` всё ещё два отдельных запроса без общей блокировки. Большой одновременный всплеск запросов всё ещё может пройти каждый свой `SELECT count` до того, как увидит INSERT'ы остальных — просто окно гонки уже, не закрыто полностью.

**Поколение 3 (0045, текущее).** Один атомарный вызов Postgres-функции.

## Почему advisory lock, а не что-то другое

Три естественных альтернативы и почему каждая не подошла:

- **Колонка-счётчик с UPSERT** (`ON CONFLICT DO UPDATE SET count = count + 1`) — самая очевидная "атомарная" альтернатива, но она требует фиксированных временных бакетов (например, "текущая минута"), а не скользящего окна. Существующая семантика — "30 запросов за последние 60 секунд, считая от текущего момента", не "30 запросов в текущей календарной минуте" — эти две вещи ведут себя по-разному на границах, и переход на бакеты был бы тихим изменением поведения, не просто рефакторингом.
- **`SELECT ... FOR UPDATE`** на существующих строках — не помогает: проблема не в конкурентном ИЗМЕНЕНИИ существующей строки, а в том, что решение "пускать или нет" принимается до того, как строка вообще создана.
- **Полная сериализация всех запросов** (глобальная блокировка) — работала бы, но без необходимости: rate limit — per-user, блокировать пользователя A, пока считается лимит пользователя B, бессмысленно и создаёт лишнюю конкуренцию под нагрузкой.

`pg_advisory_xact_lock`, взятый с двумя ключами (хэш имени таблицы + хэш `owner_id`), решает именно то, что нужно:

```sql
perform pg_advisory_xact_lock(hashtext('translate_requests'), hashtext(p_owner_id::text));
insert into public.translate_requests (owner_id) values (p_owner_id);
select count(*) into v_count from public.translate_requests
  where owner_id = p_owner_id and requested_at >= now() - make_interval(secs => p_window_seconds);
return v_count <= p_limit;
```

- Сериализует **только** конкурентные вызовы для **одного и того же** `owner_id` — запросы других пользователей друг друга никогда не блокируют.
- Держится ровно до конца транзакции (`xact_lock`, не сессионный) — снимается автоматически на `COMMIT`/`ROLLBACK`, никакого кода очистки блокировок не нужно.
- `INSERT` и `SELECT count` внутри одной функции под одной блокировкой — теперь это действительно один атомарный шаг, а не два независимых round-trip'а, между которыми может вклиниться другой запрос.
- Скользящее окно (`requested_at >= now() - N секунд`) осталось как было — семантика лимита не изменилась, изменилась только атомарность проверки.

Заодно это сократило вызов с трёх отдельных round-trip'ов к базе (`INSERT`, `SELECT count`, иногда `DELETE` для уборки старых записей) до одного RPC-вызова — побочный, но реальный выигрыш в задержке.

## Доказано числами, не только логически

Комментарий в коде мог бы просто утверждать "теперь атомарно" — вместо этого баг был **воспроизведён количественно**, до и после фикса, одной и той же нагрузкой:

`e2e/translate-rate-limit-race.spec.ts` шлёт **40 одновременных вызовов** (`Promise.all`, без задержки между ними — ровно та форма нагрузки, которую старая логика не переживала) против лимита в **10**:

```ts
const results = await Promise.all(
  Array.from({ length: CONCURRENCY }, () =>
    supabase.rpc("check_translate_rate_limit", { p_owner_id: userId, p_limit: LIMIT, p_window_seconds: 60 }),
  ),
);
const allowedCount = results.filter((r) => r.data === true).length;
expect(allowedCount).toBe(LIMIT); // ровно 10, не "примерно 10"
```

При временном воспроизведении старой (поколение 2) логики — `INSERT` → `SELECT count` без общей блокировки — под той же самой нагрузкой (40 параллельных запросов, лимит 10) прошло **12**, то есть на 20% больше разрешённого. С атомарным RPC — **ровно 10**, стабильно и детерминированно при повторных прогонах, не "плюс-минус сколько успело проскочить".

Второй assert теста — `recordedCount === CONCURRENCY` (все 40 строк реально записаны в лог) — фиксирует отдельное требование: отклонённый запрос должен быть **залогирован, но превысить лимит**, а не тихо потеряться.

## Общий вывод

"Переставить местами INSERT и SELECT" — интуитивно понятный первый инстинкт для гонки на чтение-затем-запись, и он действительно сокращает окно гонки. Но сокращённое окно — не то же самое, что закрытое: пока проверка "сколько уже было" и запись "вот ещё один" остаются двумя отдельными запросами к базе, всегда можно подобрать нагрузку (здесь — 40 параллельных вызовов), которая пройдёт между ними. Единственный способ по-настоящему закрыть такую гонку — сделать проверку и запись одной атомарной операцией на стороне базы, а не полагаться на переупорядочивание кода приложения.
