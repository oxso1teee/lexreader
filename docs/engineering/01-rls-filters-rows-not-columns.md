# RLS фильтрует строки, а не колонки — обход через SECURITY DEFINER RPC

**Код:** `supabase/migrations/0050_vocabulary_duels.sql`, `supabase/migrations/0049_weekly_leaderboard.sql`
**Проверено живьём:** `e2e/duel-privacy.spec.ts`

## Проблема одной фразой

Postgres Row Level Security решает только один вопрос: **видна ли эта СТРОКА** текущему `auth.uid()`. Она ничего не знает про отдельные колонки внутри строки, которая и так разрешена. Если в разрешённой строке лежит значение, которое должно быть видно не всегда (а по условию, зависящему от бизнес-логики, не от того, "чья это строка") — RLS сам по себе эту задачу решить не может.

## Конкретный случай: `duel_rounds.correct_answer`

В живой дуэли 1-на-1 (`duels`/`duel_rounds`/`duel_answers`) оба игрока — законные участники раунда. Формально они имеют полное право читать строку `duel_rounds` этого раунда — это буквально их собственная игра. Но `correct_answer` в этой строке — это сам ответ на вопрос, который они ещё не должны видеть **до того, как ответят**.

Обычная RLS-политика вида:

```sql
create policy "duel_rounds: participants can read" on duel_rounds
  for select
  using (exists (
    select 1 from duels d where d.id = duel_id
      and (auth.uid() = d.creator_id or auth.uid() = d.opponent_id)
  ));
```

технически честна — участник действительно имеет право читать эту строку — но она отдаёт `correct_answer` в открытом виде вместе со всем остальным. RLS не умеет сказать "разреши строку, но замаскируй одну колонку, пока не выполнено условие X" — таких политик Postgres не поддерживает.

## Решение: ноль грантов, весь доступ — через функции

`duel_rounds` и `duel_answers` в 0050 **не получают вообще ни одной policy и ни одного гранта** для `authenticated`. RLS включена (`enable row level security`), но с нулём политик это означает полный запрет — вообще никто, кроме владельца миграции (сервисной роли), не может прочитать эти таблицы напрямую через PostgREST.

Единственный путь к данным — явно перечисленные `SECURITY DEFINER`-функции, каждая из которых решает ровно одну задачу и отдаёт клиенту только то, что должно быть видно **прямо сейчас**:

- **`get_duel_state()`** — читает раунд и маскирует `correct_answer`/чужой ответ, пока раунд не завершён:

  ```sql
  'correctAnswer', case when v_round.resolved_at is not null then v_round.correct_answer else null end,
  ```

  До того как оба игрока ответили — `correctAnswer` в JSON-ответе всегда `null`, независимо от того, кто спрашивает. После — оба видят настоящий ответ.

- **`submit_duel_answer()`** — сама считает `is_correct`/`latency_ms` на сервере, не доверяя тому, что прислал клиент. Время ответа вычисляется из `duel_rounds.started_at`, а не из длительности, которую якобы отследил клиент — иначе клиент мог бы просто соврать про latency.

- **`deal_duel_round()`** и **`resolve_duel_round_timeout()`** — проверяют, что вызывающий вообще участник этой дуэли, и что это ожидаемый следующий раунд, прежде чем что-то менять.

Таблица `duels` (метаданные дуэли — статус, счёт, инициалы) — исключение: у неё **есть** обычная RLS-политика и грант `SELECT` для `authenticated`, потому что там нет ни одной "секретной" колонки, и ей обязан быть доступен Supabase Realtime (`postgres_changes` сверяет ту же RLS-политику SELECT самого коннекта, чтобы решить, доставлять ли событие). Realtime здесь используется только как сигнал "что-то изменилось, перезапроси `get_duel_state()`" — не как канал доставки самих игровых данных.

## Откуда взялся этот паттерн

Первая `SECURITY DEFINER`-функция в проекте появилась не здесь, а раньше — в `0049_weekly_leaderboard.sql` (недельный лидерборд). Там задача была другая: **обычный `authenticated`-пользователь под RLS физически не может прочитать чужие строки** `review_log`/`vocabulary_items` (везде `owner_id = auth.uid()`) — а агрегированный кросс-пользовательский рейтинг по определению требует прочитать чужую активность. `SECURITY DEFINER` там нужен, чтобы обойти RLS-запрет на чтение чужих строк вообще, и вся "привилегированность" функции жёстко ограничена тем, что именно она возвращает — только `rank`/`is_you`/инициалы/агрегированные счётчики за неделю, никогда сырые строки чужого `review_log`.

`0050` — тот же механизм (`SECURITY DEFINER` + `set search_path = ''` + явный `revoke all ... grant execute` только нужной роли), применённый к другой проблеме: не "чужие строки недоступны вообще", а "своя же строка доступна, но одна колонка должна быть условно скрыта". Задачи разные, инструмент — один и тот же, потому что оба случая сводятся к одному: **то, что видит клиент, решает функция, а не таблица**.

## Проверено живьём, не только по коду

`e2e/duel-privacy.spec.ts` создаёт трёх реальных пользователей (A создаёт дуэль, B присоединяется, C — посторонний) через анонимный ключ (не `service_role`) — то есть теми же правами, что и любой реальный клиентский код — и подтверждает границу:

- Прямое чтение `duel_rounds`/`duel_answers` через `.from(...).select("*")` **всегда возвращает пустой массив**, для всех трёх пользователей, включая законных участников.
- До того как кто-то ответил — `get_duel_state()` отдаёт `correctAnswer: null` **обоим** участникам одновременно.
- C (посторонний) не может ни прочитать состояние активной дуэли, ни присоединиться, ни сдать раунд, ни ответить — каждый RPC отдельно проверяет `auth.uid()` против `creator_id`/`opponent_id`.
- Серверная проверка времени доказана не логическим рассуждением, а прямой манипуляцией данными: тест **отодвигает `started_at` на 15 секунд назад** через `service_role` (симулируя "прошло 15 секунд" без реального ожидания), затем шлёт текстуально правильный ответ — и он всё равно засчитывается неверным, потому что латентность считается на сервере от `started_at`, а не от того, что скажет клиент.

## Общий вывод

Если в приложении когда-нибудь снова понадобится "эта строка видна, но одно её поле — только при определённом условии" — это сигнал, что RLS-политики уже недостаточно, и нужен `SECURITY DEFINER`-RPC с нулевыми прямыми грантами на таблицу, а не попытка выразить условие внутри `using (...)`.
