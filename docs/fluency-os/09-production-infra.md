# Фаза 9 — Production-слой (только с устойчивым потоком платящих)

**Ворота:** есть платящие пользователи на регулярной основе (не
разовые платежи) — до этого момента вся эта фаза приносит больше
вреда (месяцы работы на инфраструктуру) чем пользы.
**Источник:** v2, «PRODUCTION BLUEPRINT», §28–74 целиком.

Это блюпринт, а не немедленное задание. Записан подробно, чтобы
ничего не потерялось из v2, но исполняется только тогда, когда есть
что защищать и масштабировать. Ниже — сжатая, но полная версия;
детали конкретных runbook'ов — по ссылке на исходный документ, когда
дойдёт до дела.

## 9.1 Биллинг с учётом использования

Сейчас в LexReader — простой Stripe-чекаут с двумя тарифами
(`src/app/(app)/pricing/`). Для голосовых минут понадобится:

- **Entitlements** — отдельная таблица `entitlements` (feature,
  limit, period, used, source, expires_at) вместо разрозненных
  проверок `if (plan === "premium")` по всему коду. Заменяет и
  расширяет нынешний `voice_seconds_used_this_month` (Фаза 6) и
  существующие `FREE_DECK_LIMIT`/`FREE_FLASHCARD_LIMIT`/`FREE_TEXT_LIMIT`
  (`src/lib/subscription.ts`) единым механизмом.
- **Usage ledger** — таблица `usage_events` (unit: voice_seconds,
  llm_tokens, storage_bytes и т.д.) — источник правды для будущего
  биллинга по использованию сверх лимита тарифа (если решим на это
  переходить) и для расчёта `gross margin > 70%` на голосовую сессию
  (целевая метрика v2 §57).
- Инструменты: Stripe (уже используется), опционально Lago/Kill Bill
  при переходе на usage-based billing — не подключать заранее.

## 9.2 Наблюдаемость

Уже есть: PostHog (product analytics + error tracking — см.
`docs/OBSERVABILITY.md`), структурированные логи (`src/lib/log.ts`),
health-check перевода, UptimeRobot.

Добавить на этой фазе: OpenTelemetry-спаны на ключевых путях
(`ai.generate`, `voice.session`, `stripe.webhook`) — можно
экспортировать в тот же PostHog или в SigNoz/self-hosted, если объём
вырастет; Langfuse — трейсинг LLM-вызовов (промпты/ответы/латентность/
стоимость) отдельно от продуктовой аналитики, полезно именно когда
AI-компонентов становится много (Фазы 5–8 уже используют минимум
три разных LLM-вызова: extractor ошибок, extractor фраз, генерация
миссий).

## 9.3 Админка

Не строить полноценную Refine-админку сразу. Минимальная версия —
`/admin` за отдельной ролью (`profiles.is_admin boolean`), несколько
SQL-based страниц: список пользователей, статус подписок, последние
неудачные джобы, флаги злоупотреблений. Полный список из v2
(`/admin/imports`, `/admin/voice`, `/admin/feature-flags`,
`/admin/incidents`) — добавлять по одной странице по мере реальной
необходимости, не всё сразу.

## 9.4 Поддержка

Chatwoot-виджет или просто email-форма (уже есть `sendFeedback` —
`src/app/(app)/settings/actions.ts`) — расширять до полноценного
support-виджета только когда объём обращений оправдывает отдельный
инструмент (ориентир: больше 5–10 тикетов в неделю).

## 9.5 Безопасность и приватность

Уже частично сделано в этом проекте (P0-АУДИТ серии в истории задач):
rate limiting, RLS-политики, upload-валидация. Добавить на этой фазе
специфичное для голоса: явное согласие на запись (уже показано в
UI мокапе pre-session, Фаза 6) + toggle «сохранять сырое аудио» в
настройках приватности + retention policy (30 дней по умолчанию для
raw audio, если пользователь не отключил).

## 9.6 Надёжность и DR

RPO/RTO цели из v2 (15 минут / 4 часа) и ежемесячный restore test —
имеют смысл, когда есть реальные данные пользователей, которые
дорого потерять. Managed Postgres (Supabase уже managed) — проверить,
что PITR-бэкапы включены в тарифе, это часто просто чекбокс в
настройках проекта, не требует новой инфраструктуры.

## 9.7 CI/CD

Расширить текущий пайплайн (если есть) до: format → lint → typecheck
→ tests → migration check → secret scan (Gitleaks) → security scan
(Trivy/Semgrep) → build → E2E (Playwright, уже используется в
проекте) → staging → prod deploy. Добавлять шаги по одному, не всё
сразу — каждый новый шаг проверяется на реальном PR перед тем как
становится обязательным.

## Критерий готовности фазы (когда до неё дойдёт)

- Entitlements заменяют разрозненные лимит-проверки.
- Usage ledger пишется для голосовых сессий, gross margin считается.
- Restore test проведён минимум один раз вручную.
- Release-gate чеклист (см. `10-full-ui-system.md`) пройден целиком.
