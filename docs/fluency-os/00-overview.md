# LexReader Fluency OS — набор промптов для реализации

Источник: три планирующих документа пользователя —
`LexReader_Fluency_OS_Startup_Plan.md` (2 497 строк),
`LexReader_Fluency_OS_Startup_Plan_v2_Production.md` (4 185 строк),
`LexReader_Startup_Master_Plan_v3_Product_UI_Release.md` (6 477 строк) —
суммарно 13 159 строк. Разобраны полностью, вердикт по ним —
в артефактах `docs/FLUENCY_OS_VISION_2026-07-31.html` и
`docs/FLUENCY_OS_VISION_ALL3_2026-07-31.html`.

Этот каталог (`docs/fluency-os/`) — не пересказ тех документов, а
исполнимая версия: каждый файл — законченный промпт для AI coding
agent (Claude Code/Codex), с точными путями файлов, SQL, схемами
компонентов и критериями готовности — того же уровня детализации,
что `docs/IMPLEMENTATION_PROMPT_2026-07-30.md`, который в этом же
проекте уже был полностью выполнен за одну сессию.

## Почему файлы, а не один гигантский промпт

Все три исходных документа сами себе противоречат: они требуют от
AI-агента «маленьких проверяемых срезов» (v1, раздел 18; v2, раздел
71; v3, раздел 148) — и тут же описывают монорепо на пять сервисов,
20 таблиц и ~70 маршрутов как единую спецификацию. Один
промпт-исполнитель не может одновременно быть «маленьким срезом» и
«полной production SaaS-платформой».

Поэтому: **каждый файл ниже — это самостоятельная фаза с воротами
(gate)**. Ворота — это проверяемое условие, при котором имеет смысл
переходить к следующему файлу. Фазы 1–3 можно начинать сегодня же.
Фазы 5+ открываются только после реальной проверки спроса (Фаза 4).
Это не бюрократия — это единственный способ не потратить месяцы на
инфраструктуру, которая никому не нужна.

## Общие инженерные правила (для всех фаз)

Синтез правил из всех трёх документов (v1 §18, v2 §71, v3 §148) плюс
уже действующие в этом проекте конвенции — см. `AGENTS.md` в корне
репозитория, они имеют приоритет там, где противоречат этому файлу.

1. Не переписывать существующий LexReader с нуля. Каждая фаза —
   аддитивна к текущему Next.js-монолиту, пока явно не сказано иное.
2. Не удалять работающую функциональность без доказанной необходимости.
3. Не копировать код из GPL/AGPL-репозиториев (см. таблицу лицензий
   в конце `docs/FLUENCY_OS_VISION_ALL3_2026-07-31.html`) — особенно
   OpenMAIC, Intro.js, OpenStatus.
4. Изменения — маленькими проверяемыми срезами. После каждого среза:
   `npx tsc --noEmit`, `npx eslint`, ручная проверка в браузере через
   Browser-панель, только потом коммит.
5. Не коммитить секреты/API-ключи. Новые переменные окружения — в
   `.env.local.example` с комментарием, откуда их взять.
6. Каждая новая таблица — отдельная миграция в `supabase/migrations/`,
   применяется и локально (Docker), и в проде (через Management API),
   как это делалось для всех предыдущих миграций в этом проекте.
7. Не заявлять, что функция готова, не проверив её вживую (полный
   пользовательский сценарий в браузере, не только typecheck).
8. Комментарии в коде — только там, где неочевидно "почему", без
   комментариев "что" (см. правило проекта в `AGENTS.md`/системном
   промпте) и без ссылок на номер фазы/задачи в самом коде.
9. Тексты интерфейса — по правилу v3: конкретика вместо хайпа
   («Пройди 7-минутную симуляцию интервью», не «Открой мощь ИИ»).
10. Каждый новый экран — с честными состояниями loading/empty/error,
    не бесконечным спиннером и не пустым списком без объяснения.

## Definition of Done для любой фазы

Фаза считается завершённой, только если:

- есть критерий приёмки (сформулирован в файле фазы) и он проверен вручную;
- миграция применена и в Docker, и в проде;
- новый UI имеет loading/error/empty-состояния;
- `npx tsc --noEmit` и `npx eslint` проходят чисто;
- happy path проверен в браузере (не только код скомпилировался);
- секреты не попали в git;
- документация (`docs/OBSERVABILITY.md` и т.п., если применимо) обновлена;
- production build (`npm run build`) проходит;
- задеплоено и живьём проверено на проде.

## Как использовать эти файлы с Claude Code / Codex

Для каждой фазы: открыть соответствующий файл, скопировать его
целиком в новый запрос агенту (или просто сослаться на путь файла —
Claude Code умеет читать файлы по пути). Не запускать сразу
несколько фаз параллельно — ворота существуют именно для
последовательного исполнения. После завершения фазы — отметить это
в `docs/fluency-os/00-overview.md` (в этой самой таблице) и переходить
к следующей, если ворота открыты.
