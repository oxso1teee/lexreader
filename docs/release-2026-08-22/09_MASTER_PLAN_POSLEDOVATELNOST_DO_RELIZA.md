# 09 — Мастер-план: последовательность до отправки в сторы

Собирает файлы 00-08 в одну исполняемую последовательность по вехам.
Каждая веха — законченный кусок, который можно отдать целиком одной
сессии Claude Code с промптом "выполни веху M2 из
`09_MASTER_PLAN_POSLEDOVATELNOST_DO_RELIZA.md`". Не перепрыгивай вехи —
каждая следующая опирается на то, что предыдущая реально сделана и
проверена (не "вроде должно работать", а прогнаны тесты/чек-листы).

## M0 — Синхронизация (файл 08)

**Что делаем**: разбираемся с расхождением локальной машины и GitHub —
пушим/мержим готовую работу по видео-ридеру, решаем судьбу воркера и
`research/`, чистим репозиторий.

**Готово, когда**: `git status` на локальной машине чист (или
осознанно оставлены только явно временные файлы), `main` на GitHub
соответствует тому, что реально работает и протестировано.

## M1 — Безопасность и деньги (файлы 02, 03)

**Что делаем**: `npm audit fix` (без `--force`) для `pdfjs-dist`,
заводим рабочий email поддержки, чиним кэш переводов и race condition в
рейт-лимите, перепроверяем и закрываем оставшиеся абьюз-векторы
(лимиты free-тарифа, MIME-проверка Storage), решаем вопрос
масштабирования перевода (MyMemory лимит 5000 слов/день — файл 03,
раздел 4) до того, как появится приток пользователей из сторов.

**Готово, когда**: `npm audit` чист от high-severity в собственном коде
и легко фиксируемых транзитивных, все пункты раздела A/B файла 02
закрыты, файл 03 раздел 4 имеет явное решение (не обязательно
реализовано, но выбран план: платный MyMemory / LibreTranslate / DeepL).

## M2 — Обновление Next.js (файл 02, A.2)

**Что делаем**: отдельной задачей, не смешивая с остальным — апгрейд
Next.js до версии, закрывающей 4 high-severity CVE, с полным прогоном
тестов и e2e после.

**Готово, когда**: `npm audit` чист и по Next.js, весь набор тестов
(`npm run test:ui`, `test:srs`, `test:fsrs`, `test:import`,
`test:extension`, `test:csp`, `npx playwright test`) зелёный на новой
версии.

## M3 — Юридическая база (файл 05, частично файл 03 раздел 2)

**Что делаем**: актуализируем Terms/Privacy под реальное поведение
оплаты, добавляем контакты, подпроцессоров, место хранения данных;
явно решаем вопрос 152-ФЗ (хотя бы одна консультация, если аудитория
— Россия); проходим опросник возрастного рейтинга.

**Готово, когда**: Terms и Privacy дословно соответствуют коду и друг
другу, есть черновик текста для форм Data Safety/Privacy Nutrition
Label.

## M4 — Мобильная стратегия: решение (файл 04, разделы 1-2)

**Что делаем**: НЕ код — решение. Определяешь бизнес-статус (ИП/нет),
приоритет сторов (RuStore vs Google Play vs Apple), стратегию оплаты
на каждом сторе (StoreKit/Play Billing vs внешняя ссылка vs "оплата
только на сайте"). Это тот самый момент, где стоит либо явно
зафиксировать решение самому, либо вернуться ко мне с готовыми
ответами, чтобы я помог довести технически.

**Готово, когда**: у тебя есть письменный (пусть даже на пару абзацев)
ответ на все пункты раздела 5 файла 04.

## M5 — Мобильная обёртка: реализация (файл 04, разделы 3-4, файл 06 частично)

**Что делаем**: доводим PWA (`manifest.json`, `sw.js`, offline-страница)
до полноценного состояния; собираем Capacitor-проект под Android;
проходим сценарии из файла 06 "Приоритетнее прочих" и "Локализация" —
это тот момент, когда мелкие UX-огрехи становятся видны конкретному
живому человеку с телефоном в руке, а не абстрактному пользователю.

**Готово, когда**: APK/AAB собирается, устанавливается на реальный
телефон, полный путь пользователя (регистрация → импорт → чтение →
повторение → настройки → удаление аккаунта) проходится руками без
падений.

## M6 — Тестовые пробелы и CI (файл 07)

**Что делаем**: закрываем тесты на delete/export аккаунта,
идемпотентность Stripe webhook, RLS-регрессию, PDF-импорт (по
приоритету из файла 07, раздел 4).

**Готово, когда**: перечисленные тесты существуют и проходят в CI, не
только "проверено руками один раз".

## M7 — Материалы и публикация (файл 05, разделы 5-6)

**Что делаем**: иконки, скриншоты, описания, ключевые слова под каждый
стор; финальный чек-лист файла 05 раздел 6 — каждый пункт отмечен;
заводим/оплачиваем аккаунты разработчика; отправляем на ревью.

**Готово, когда**: приложение отправлено на ревью хотя бы в один стор.
Ревью Apple может занять несколько итераций отказ/фикс/пересдача — это
нормально, закладывай на это отдельное время после отправки, не
считай M7 законченной вехой в момент "нажал кнопку Submit".

## Как использовать этот файл с Claude Code

Когда будешь готов выполнять конкретную веху — открой новую сессию (или
эту же) и напиши примерно так: "Выполни веху M1 из плана в
`docs/release-2026-08-22/09_MASTER_PLAN_POSLEDOVATELNOST_DO_RELIZA.md`,
опирайся на файлы 02 и 03 из той же папки". Не проси выполнить весь
план разом одним промптом — вехи specifically разбиты так, чтобы
помещаться в разумный объём работы за один заход и чтобы после каждой
можно было проверить результат перед тем, как двигаться дальше. Именно
отсутствие такой дисциплины (десятки параллельных аудитов и слайсов без
единой последовательности) — то, что привело к нынешнему объёму
документации в `docs/`, часть которой уже устарела быстрее, чем её
дочитали. Не повторяй этот паттерн с этим планом — если что-то из
файлов 01-08 устареет по мере работы, лучше явно пометить пункт
"[УСТАРЕЛО, см. факт Х]" прямо в файле, чем плодить десятый по счёту
параллельный документ с тем же названием и новой датой.
