# 03 — Безопасность и приватность данных

Дополняет файл 02 (там — конкретные баги). Здесь — системные вопросы:
какие данные вообще собираются, где хранятся, что по закону нужно про
них сказать пользователю, и какие абьюз-векторы остаются открытыми на
уровне архитектуры, а не одной строчки кода.

## 1. Какие персональные данные реально собирает приложение

Составлено по факту наличия таблиц/интеграций в коде — понадобится
дословно для Privacy Policy и для форм Data Safety (Google)/Privacy
Nutrition Label (Apple), файл 05:

- **Email + хеш пароля** — Supabase Auth.
- **Фото** — при OCR-импорте слов/текста (`word-photos` storage bucket,
  фото к словам в Тетради). Хранятся ли они постоянно или удаляются
  после распознавания — нужно явно проверить и написать в политике.
- **Платёжные данные** — не хранятся у тебя напрямую (обрабатывает
  Stripe), но `stripe_customer_id` и статус подписки — да, в своей БД.
- **Тексты, которые пользователь импортирует** (URL-статьи, YouTube-
  транскрипты, PDF, сфотканные страницы) — потенциально это чужой
  авторский контент, не только "данные пользователя" (см. раздел 3).
- **Слова/фразы, которые пользователь ищет и сохраняет** — по сути,
  история обучения; в связке с Language Twin это ещё и поведенческий
  профиль ошибок пользователя.
- **PostHog** — аналитика использования, вероятно с client-side event
  tracking. Нужно явно аудировать (`docs/audit/ai-analytics-map.md`
  уже claim'ит, что PII туда не идёт — перед релизом стоит перепроверить
  вживую через `read_network_requests`/логи PostHog, что события не
  тащат email/токены в свойствах).
- **IP-адрес** — используется для rate-limit (`auth_attempts`,
  `translate_requests`) — тоже персональные данные по большинству
  юрисдикций (включая 152-ФЗ РФ и GDPR).

## 2. Российское законодательство (152-ФЗ) — вероятный слепой пункт

Судя по интерфейсу (полностью русский, цены в рублях, Условия/Политика
на русском) — целевая аудитория как минимум частично в РФ. 152-ФЗ
"О персональных данных" требует **локализации хранения и обработки
персональных данных граждан РФ на серверах, физически расположенных на
территории России**, за отдельными исключениями. Supabase (используемый
как БД+Auth+Storage) по умолчанию хостится не в РФ (AWS/облако вне
России). Это отдельный, не техническо-баговый, а юридический риск —
не тема, которую можно закрыть кодом, нужно либо: (а) юридическая
консультация о применимости 152-ФЗ к конкретно этому продукту и
масштабу, (б) явное упоминание в Политике конфиденциальности, где
физически хранятся данные, и на каком основании (согласие пользователя
на трансграничную передачу — 152-ФЗ это допускает при явном
информированном согласии в определённых случаях). **Не игнорируй этот
пункт просто потому что "все так делают"** — при реальном масштабировании
на российскую аудиторию это то, что может привести к блокировке
Роскомнадзором, если на приложение пожалуются или оно попадёт в поле
зрения. Для этапа "тест на живых людях/soft launch" риск невысокий, но
перед серьёзным маркетингом на русскоязычную аудиторию — нужна хотя бы
одна консультация с юристом, специализирующимся на 152-ФЗ.

## 3. Авторские права на импортируемый контент

Библиотека позволяет импортировать: статьи по URL, YouTube-транскрипты,
PDF, тексты с фото. Это чужой контент (статьи, субтитры), не
пользовательский. Модель использования (личное некоммерческое изучение
языка, текст не публикуется другим пользователям) — низкий риск, но:
убедись, что Условия использования явно возлагают ответственность за
законность источника на самого пользователя (типичная формулировка
"вы подтверждаете, что имеете право использовать импортируемый контент
в личных целях"), и что импортированные тексты **не расшариваются между
пользователями** (то есть это не превращается в пиратскую библиотеку
книг/субтитров). Стоит явно проверить, есть ли хоть один путь, которым
текст одного пользователя виден другому (RLS должен это исключать —
но стоит формально подтвердить тестом, раздел 07).

## 4. Абьюз-векторы, которые не баг, а осознанный выбор архитектуры

Не критично для маленького масштаба, но стоит знать заранее, до того как
появится реальная нагрузка:

- **MyMemory (бесплатный переводчик) — общий лимит ~5000 слов/день на
  всё приложение**, как явно написано в `README.md`. При росте
  пользователей это узкое место номер один, причём не техническое —
  один активный день использования "положит" перевод для всех
  остальных пользователей одновременно. Перед публичным релизом в сторы
  (то есть перед потенциальным резким ростом установок) нужно решить:
  платный тариф MyMemory, переход на LibreTranslate (self-hosted,
  упомянут в README как запасной вариант), или DeepL. Это НЕ то, что
  можно отложить на "после релиза" — если про приложение узнают из
  стора и придёт больше 100 активных пользователей в один день, перевод
  перестанет работать для всех сразу, в момент, когда важнее всего
  произвести хорошее первое впечатление.
- **Free-tier лимиты (3 текста/3 колоды и т.д.) обходятся технически
  подкованным пользователем через прямой вызов Supabase REST API** —
  частично закрыто триггером БД (`0019_free_tier_db_backstop.sql`, файл
  02 раздел C) — если триггер покрывает не все таблицы, это открытая
  дыра для потери денег (кто-то делится обходным путём в комментариях/
  чатах — не гипотетический сценарий для инди-приложения).
- **Хранилище (Storage) MIME-проверка смотрит только на заголовок
  `Content-Type`, не на реальное содержимое файла** — из июльского
  аудита, статус не перепроверял сегодня. При прямом API-вызове
  (не через обычную загрузку в интерфейсе) можно подменить тип файла.
  Не критично при текущем масштабе, но стоит закрыть до масштабного
  роста — например через магические байты (`file-type` npm-пакет).

## 5. npm-зависимости (дополнение к файлу 02)

Файл 02 раздел A.1/A.2 покрывает `pdfjs-dist` и `next` — обе high-severity.
Также `sharp` и `postcss` (транзитивные, через `next`) — фиксируются тем
же апгрейдом Next.js. После любого апгрейда зависимостей — обязательно
`npm audit` заново, это должно стать частью чек-листа перед каждым
релизом (файл 07 — предложение вынести в CI).

## 6. Что делать с этим файлом

Раздел 1 (инвентарь данных) — прямой вход в файл 05 (юридические формы
для сторов), перенеси его дословно туда при заполнении форм. Раздел 2
(152-ФЗ) — реши отдельно от остального плана, это не блокирует
техническую готовность к сторам, но блокирует безопасный рост на
русскоязычную аудиторию, и решение здесь юридическое, не инженерное.
Разделы 3-5 — рабочие задачи, раздели между собой и файлом 02.
