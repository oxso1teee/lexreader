# 07 — Тестирование и CI перед релизом

База уже сильная (файл 01, раздел 1) — 386 unit-тестов, 18 e2e-файлов,
CI гоняет typecheck/lint/build на каждый push плюс отдельный e2e-job с
реальным Supabase. Это не "добавить тесты с нуля", а закрыть конкретные
дыры и подготовить CI к тому, что после публикации в сторах откатывать
плохой релиз станет дороже (нельзя просто "перезалить Vercel" — на
исправление в App Store уйдут дни на повторное ревью).

## 1. Тестовые пробелы, которые стоит закрыть перед публикацией в сторах

- **Регрессионный тест на RLS** — сейчас (по `docs/audit/test-gap-map.md`
  от 01.08, вероятно ещё актуально) RLS проверялся только код-ревью
  миграций, не автоматическим тестом, что чужие данные реально
  недоступны. Для приложения с деньгами и персональными данными
  пользователей это стоит закрыть отдельным e2e/интеграционным тестом:
  два тестовых пользователя, один пытается прочитать/изменить данные
  другого напрямую через Supabase-клиент — тест должен подтверждать
  отказ на каждой чувствительной таблице (`subscriptions`, `texts`,
  `vocabulary_items`, `decks`, `flashcards`).
- **Тест на идемпотентность Stripe webhook** — что повторная доставка
  одного и того же `event.id` (Stripe гарантированно иногда шлёт дубли)
  не создаёт вторую подписку/не начисляет дважды. Файл 02/03 упоминают
  отсутствие таблицы обработанных `event.id` — сначала нужен сам фикс
  (добавить таблицу + проверку), тест пишется вместе с ним.
- **PDF-импорт** — ни unit, ни e2e теста нет (по состоянию на 01.08).
  Особенно важно после фикса уязвимости `pdfjs-dist` (файл 02, A.1) —
  тест должен подтверждать, что импорт нормального PDF работает и что
  результат апгрейда/патча зависимости ничего не сломал.
- **Delete/Export аккаунта** — ни unit, ни e2e (по состоянию на 01.08).
  Обязательный сценарий, раз Apple прямо требует рабочее удаление
  аккаунта внутри приложения (файл 05) — стоит закрыть e2e-тестом,
  который реально создаёт пользователя, удаляет его и проверяет
  каскадное удаление данных.

## 2. Специфично для мобильной обёртки (после файла 04)

- **Смоук-тест на реальном устройстве** перед каждой отправкой в ревью:
  установка APK/сборки на физический телефон (не только эмулятор),
  прохождение полного пути — регистрация → импорт текста → чтение →
  повторение карточек → (если подключено) оплата. Автоматизировать
  сложно и не обязательно для первого релиза — но зафиксировать как
  ручной чек-лист перед каждой отправкой.
- **Проверка deep link/push на нативной сборке** — если добавляешь
  Universal Links/App Links и нативный push (файл 04), это плохо
  покрывается существующими Playwright e2e (они гоняются против веб-
  версии) — нужен отдельный ручной или Capacitor-специфичный прогон.
- **Offline-режим** — проверить `src/app/offline/page.tsx` и
  `public/sw.js` в реальных условиях (авиарежим на телефоне) — стор-
  ревьюеры (особенно Apple) иногда специально тестируют приложение без
  сети и без результата дают отказ за "не работает офлайн" даже если
  формально это не заявленная фича — стоит хотя бы аккуратно показать
  понятный офлайн-экран, а не белый "Application error".

## 3. Улучшения CI (не блокирует релиз, но снижает риск регрессии)

- **`npm audit` как отдельный шаг CI**, который явно падает (или хотя
  бы предупреждает в Slack/email) на новых high-severity уязвимостях —
  сейчас находки вроде `pdfjs-dist` (файл 02) можно узнать только
  вручную запустив команду. Дёшево добавить, сильно снижает риск
  пропустить следующую подобную находку.
- **Синхронизация версии Node между локальной машиной и CI** — по
  `docs/audit/2026-08-current-state.md` локально v22, в CI указано `20`
  (сейчас `.github/workflows/ci.yml` уже переключён на `22`, судя по
  проверке сегодня — если так, пункт уже закрыт, просто зафиксировать).
- Опционально, не обязательно для маленькой команды из одного
  человека: security-сканеры в CI (Semgrep/Trivy/Gitleaks) — про них
  писал `docs/audit/2026-08-current-state.md` как отсутствующие; полезно
  при росте кодовой базы, не критично прямо сейчас.

## 4. Порядок

Не пытайся закрыть весь файл разом. Порядок по критичности для релиза
в сторы: Delete/Export аккаунта (юридически обязательно для Apple) →
идемпотентность Stripe webhook (реальные деньги) → RLS-регрессия
(приватность данных) → PDF-тест (безопасность, связано с файлом 02) →
мобильные смоук-тесты (после того как появится сама обёртка, файл 04) →
CI-улучшения (в любой момент, не блокирует).
