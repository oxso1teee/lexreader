# M3 Slice 12 — Gate #2C: browser extension as the primary YouTube ingestion path

## Why

Gate #2B found real, measured evidence that the server-side worker doesn't
survive contact with genuinely free hosting: Render Free's shared egress IP
is already rate-limited by YouTube (3/3 real attempts failed identically at
the metadata-fetch stage), and separately faster-whisper hit Render's 512MB
ceiling 1,958 times on the smallest possible test clip. The worker is
**parked**, not deleted — see `worker/youtube-ingestion/` — kept intact for
a future paid deployment. For the current zero-cost build, the browser
extension bridge becomes the **primary** ingestion path.

## Why the old extractor was broken

The pre-Gate-#2C bridge (`youtube-transcript.mjs`'s `fetchYoutubeTranscript`)
fetched the watch page HTML and the caption track's `baseUrl` directly from
the extension's background service worker context. Real testing this
session reproduced the exact failure: that fetch gets a real `HTTP 200` but
an **empty body**. YouTube's `/api/timedtext` endpoint now requires a `pot`
(Proof-of-Origin Token) query parameter, generated by YouTube's own
in-page BotGuard challenge — a bare `fetch()`, even from real page-context
JS, never carries a valid one.

## The fix: observe, don't fetch

Real, live testing (via a real browser tab, not synthetic) found that
YouTube's own player **already issues** a pot-bearing `/api/timedtext`
request automatically on normal video load (for the video's default
caption track) — and that opening the real "Show transcript" panel makes
YouTube issue the same authenticated request for a specific language on
demand. Two more real findings refined the mechanism:

1. **It's XMLHttpRequest, not `fetch()`.** The real request goes out via
   XHR. A capture script that only patches `window.fetch` silently misses
   it — confirmed via Playwright's own network log (`resourceType: "xhr"`).
   `youtube-page-capture.js` patches both.
2. **`navigator.webdriver` matters.** A Playwright-launched Chromium
   (`navigator.webdriver === true`) gets the *same* real pot-bearing
   request, `HTTP 200`, but an **empty body** — YouTube's server silently
   withholds content from automation-flagged sessions rather than erroring.
   The same code with `navigator.webdriver === false` (verified both via a
   separate real Electron-Chromium browser, and via
   `--disable-blink-features=AutomationControlled` on Playwright itself)
   gets the real transcript. This only affects the *test harness's*
   fingerprint — a real user's real Chrome never sets this flag, so nothing
   about the shipped extension needs to work around it.

We never try to synthesize the `pot` token. We only ever observe a request
YouTube's own trusted code already made and already authenticated.

## Architecture

- `youtube-page-capture.js` — **MAIN world** content script on
  `youtube.com/watch*`, `document_start`. Patches `fetch`/`XMLHttpRequest`
  to observe (never intercept/replace) `/api/timedtext` responses, and
  polls `window.ytInitialPlayerResponse` for title/duration. Dispatches
  `CustomEvent`s on `document` — the standard bridge for MAIN-world page JS
  to reach the extension's isolated world.
- `youtube-content-relay.js` — **isolated world** content script on the
  same pages. Buffers captures, and on a `LEXREADER_EXTRACT_FROM_PAGE`
  request from the background service worker: waits up to 4s for the
  video's default track to auto-capture; if that doesn't match the target
  language, clicks the real transcript-panel button and waits again for a
  fresh, correctly-authenticated capture. Never invents data — returns
  `transcript_unavailable` if nothing was captured.
- `background.mjs` — unchanged origin-allowlist/PING handling for the
  LexReader-tab side; the transcript-request handler now finds or opens a
  real `youtube.com` tab (new `tabs` permission), waits for its content
  script to announce ready, messages it, and normalizes the raw capture via
  `buildTranscriptResult()`. Closes only tabs it created itself.
- `youtube-transcript.mjs` — pure parsing only now (`extractVideoId`,
  `parseJson3Segments`, `buildTranscriptResult`). The old network-fetching
  `fetchYoutubeTranscript` is gone.

## Persistence

Browser-extracted transcripts flow through the exact same central import
service the (parked) worker path uses —
`startYoutubeImportFromBrowserAction()` validates the payload via
`assertValidTranscriptResult()` (defense-in-depth; the extension is
untrusted input) and calls `runYoutubeImport()` with a synchronous
`callWorker` that just wraps the already-extracted result. No import or
dedup logic is duplicated between paths.

## Disclosed limitation

Language targeting isn't fully solved: if a video's automatically-captured
default track doesn't match the user's target language, clicking the
transcript-panel button opens the panel but doesn't reliably force a
specific-language selection (that would need driving the panel's own
language dropdown, not implemented here). The extension currently returns
whichever real, correctly-timed track it did capture rather than inventing
or blocking on an unavailable one — honest behavior, not a silent
mismatch, but not perfect targeting either.
