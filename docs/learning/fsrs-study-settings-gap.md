# Study Settings vs FSRS — что перестаёт влиять на планирование

Экран `/brain/settings` (`src/app/(app)/brain/settings/settings-form.tsx`)
не менялся в фазе M2/FSRS Release Review — все поля продолжают
отображаться и сохраняться в `srs_settings` независимо от
`FSRS_ENABLED`. Этот документ фиксирует, какие из них реально влияют на
расчёт интервала при каждом из двух алгоритмов, чтобы решение
"скрыть/переименовать/оставить" можно было принять осознанно, отдельно
от этой ветки.

## Продолжают работать при любом значении `FSRS_ENABLED`

Эти поля не про формулу интервала — они управляют очередью и
UI, не пересекаются с алгоритмом:

| Поле | Где используется |
|---|---|
| `new_cards_per_day` | лимит новых карточек в очереди повторения |
| `max_reviews_per_day` | лимит повторений в очереди |
| `study_direction` | направление показа (слово→перевод / перевод→слово) |
| `show_timer`, `autoplay_audio` | косметика UI ревью |

## Работает только при `FSRS_ENABLED=false` (SM-2), инертно при `true`

| Поле | Роль в SM-2 (`src/lib/srs.ts`) | Что происходит при FSRS |
|---|---|---|
| `starting_ease` | начальный `ease_factor` НОВОЙ карточки (задаётся один раз при создании — `src/lib/vocabulary.ts`, `brain/actions.ts`, `brain/[deckId]/actions.ts`, `read/[textId]/actions.ts`, `starter-deck-actions.ts`) | FSRS не использует "ease factor" как концепцию — новая карточка всегда стартует с `createEmptyCard()` (`src/lib/fsrs.ts`), это поле не читается FSRS-веткой вообще |
| `easy_bonus` | множитель интервала при оценке "Легко" | нет аналога — у FSRS нет отдельного бонус-множителя, "лёгкость" уже часть 4-балльной модели `stability`/`difficulty` |
| `interval_modifier` | глобальный множитель на все интервалы | нет аналога в `generatorParameters` (это не то же самое, что `request_retention`, который в этой фазе не выведен в UI — см. ниже) |
| `graduating_interval_days` | интервал первого успешного повторения | у FSRS этот интервал — не константа, а функция `stability`/`difficulty`, посчитанная моделью |
| `easy_interval_days` | интервал первого повторения при "Легко" | аналогично — FSRS считает это сам |

## Есть прямой аналог, перенесён

| Поле | SM-2 | FSRS |
|---|---|---|
| `max_interval_days` | `DEFAULT_SRS_PARAMS.maxIntervalDays` | `generatorParameters({ maximum_interval })` — **единственное** поле `srs_settings`, которое реально передаётся в `reviewFsrsCard()` (см. `actions.ts`) |

## Параметры FSRS, которых вообще нет в UI (ни при каком значении флага)

`src/lib/fsrs.ts` жёстко задаёт `enable_fuzz: true`, `enable_short_term: false`
и не передаёт `request_retention`/`w` (веса модели) — используются
дефолты `ts-fsrs`. Пользователь не может их настроить ни через
существующий экран, ни через новый — это не "сломанная" настройка, а
просто ещё не реализованная возможность конфигурации. Стоит явно
отделять от таблицы выше: это не regression, а нереализованная фича.

## Что видит пользователь сейчас

Ничего не изменилось визуально: те же 9 полей на `/brain/settings`,
без пометок "не действует" или "только для старого алгоритма" — потому
что `FSRS_ENABLED` сейчас не включён нигде (даже локально), так что
для 100% пользователей все поля прямо сейчас делают то, что написано.
Несоответствие становится реальным только в момент, когда флаг
включат — до этого момента это не UX-баг, а задокументированный риск
на будущее.

## Почему это не должно блокировать shadow rollout

Shadow-режим (`FSRS_ENABLED=false`, но FSRS считается и пишется в
`fsrs_*`/`review_log` на каждом ревью) не показывает пользователю
никакого расписания на основе FSRS — `due_at` полностью решает SM-2, и
все перечисленные выше настройки продолжают быть на 100% активными.
Ничего в этом документе не мешает мёржу этой ветки или наблюдению за
накапливаемой FSRS-историей.

## Должно ли это блокировать включение FSRS для всех пользователей

Да, частично — не технический блокер (обе схемы данных и алгоритм уже
работают корректно, см. `fsrs-test-report.md`), а UX/доверие: включение
`FSRS_ENABLED=true` глобально без изменения экрана Study Settings
означает, что пользователь может подвинуть, например, `easy_bonus`,
увидит, что значение сохранилось, но не увидит никакого эффекта на
свои интервалы — это вводит в заблуждение. Рекомендация (не
реализовано в этой фазе намеренно, вне её scope): перед полным
включением `FSRS_ENABLED=true` для всех пользователей либо скрыть
неактивные при FSRS поля, либо явно пометить их как "действует только
в классическом режиме". Ограниченный внутренний/тестовый rollout (см.
`fsrs-rollout.md`, пункт "Ограниченный rollout по пользователям") может
проходить и без этого — там пользователи предупреждены явно, вне UI.
