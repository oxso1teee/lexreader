## Known limitations / открытые риски

1. **Причина инцидента, для будущих rollout'ов**: аддитивная миграция и
   код, который на неё опирается, должны либо применяться СТРОГО перед
   деплоем зависимого кода, либо код должен переносить работу с новыми
   колонками в отдельный шаг после подтверждённого применения миграции.
   В этой фазе задание явно требовало "сначала код с выключенным флагом,
   потом миграция" — но не предупреждало, что уже смёрженный код
   безусловно (независимо от `FSRS_ENABLED`) обращается к колонкам новой
   миграции для shadow-вычислений, из-за дизайна "считать FSRS в тени
   всегда". Это несовместимо с раздельным деплоем кода и миграции для
   ЭТОЙ конкретной реализации — на будущее стоит либо (a) делать
   shadow-запись условной по факту наличия колонок / try-catch вокруг
   самого DB-обращения (не только вокруг `computeFsrsShadowSafe`,
   который защищает от ошибок ВЫЧИСЛЕНИЯ, а не от ошибки `.select()`
   несуществующих колонок на уровне БД), либо (b) всегда применять
   миграцию непосредственно перед деплоем зависимого кода в одном
   контролируемом окне.
2. Backup/PITR отсутствуют на текущем тарифе Supabase (Free) — блокирует
   любую будущую попытку применить `0032` до отдельного решения.
3. CI e2e-проверка red по несвязанной причине (Node 20 vs требование
   Node 22+ для `@supabase/realtime-js`) — не относится к этому
   инциденту, отдельный follow-up.
4. Study Settings gap — без изменений, см.
   `docs/learning/fsrs-study-settings-gap.md`, не относится к текущему
   инциденту.

## Безопасный план повторного rollout (запрошен явно)

1. **Backup/PITR сначала** — апгрейд Supabase-проекта на Pro-план (даёт
   scheduled backups + опцию PITR) ИЛИ ручной `pg_dump`-снимок
   production БД как временная мера. Отдельное решение владельца,
   не выполнено в этой фазе.
2. **Устранить причину инцидента в коде** (пункт 1 из "Открытые риски")
   — прежде чем повторно деплоить `f116aaa`-эквивалентный код, либо
   применить миграцию `0032` непосредственно перед деплоем в одном
   окне, либо изменить `reviewWord()`/`fsrs.ts` так, чтобы shadow-запись
   не падала при отсутствии колонок (аналогично уже существующему
   `computeFsrsShadowSafe`, но на уровне самого DB-обращения). Это
   реализационная работа, требующая отдельного явного задания — не
   выполнялась в рамках этой фазы (вне её scope: "не менять
   FSRS-архитектуру").
3. Применить `0032_fsrs_state.sql` к production сразу после (1),
   максимально близко по времени к следующему деплою кода.
4. Задеплоить код с `FSRS_ENABLED=false` сразу после (3).
5. Провести production smoke test (логин, review session, все 4
   кнопки, due count, statistics) — в этот раз с заранее заведённым
   безопасным тестовым аккаунтом в production, а не только
   структурной проверкой.
6. Понаблюдать за shadow-данными некоторое время.
7. Только после этого — отдельная, явно запрошенная Phase 2 (решение
   о `FSRS_ENABLED=true`).

`FSRS_ENABLED` остаётся `false`/не задан на всём протяжении этой фазы.
FSRS не включался ни на одном этапе. Language Twin не начинался.
