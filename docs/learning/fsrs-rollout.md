# M2 Learning Upgrade — feature flag, rollout, rollback

## Флаг

`FSRS_ENABLED` — server-side переменная окружения (НЕ `NEXT_PUBLIC_*`,
недоступна клиенту напрямую). Единственное место, где она реально
читается — `src/lib/fsrs.ts` (`isFsrsEnabled()`):

```ts
export function isFsrsEnabled(): boolean {
  return process.env.FSRS_ENABLED === "true";
}
```

Поведение:

```
не задана, пусто, "false", любое другое значение → false → SM-2 авторитетен для due_at
точная строка "true"                              → true  → ts-fsrs авторитетен для due_at
```

Безопасное значение по умолчанию — `false`: если переменная не
задана нигде (как сейчас, ни в `.env.local`, ни в проде), поведение
не меняется относительно того, что уже работало до этой фазы.

## Почему это не «клиентский флаг как единственная защита»

`isFsrsEnabled()` вызывается только из серверного кода:

- `src/app/(app)/brain/[deckId]/review/actions.ts` (`reviewWord`) —
  единственное место, где флаг решает, какой `due_at` реально
  запишется в БД. Это server action, клиент не может передать сюда
  собственное значение флага — функция ничего не принимает параметром
  извне для этого.
- `src/app/(app)/brain/[deckId]/review/page.tsx` — server component,
  вычисляет `fsrsEnabled` один раз при рендере страницы и передаёт
  вниз как обычный React-проп в `ReviewModeSwitcher` → `ReviewSession`.

Клиентский компонент (`review-session.tsx`) получает уже готовое
значение только для одной цели — выбрать, чьей формулой посчитать
**предпросмотр** интервала на кнопках оценки (косметика, ничего не
сохраняет). Даже если бы кто-то подделал этот проп через devtools,
реальное сохранение оценки всё равно идёт через `reviewWord`,
которая не доверяет клиенту и проверяет `process.env.FSRS_ENABLED`
заново на сервере.

## Rollout

1. **Сейчас (эта фаза):** `FSRS_ENABLED` не задана нигде. SM-2
   полностью авторитетен, как и до миграции. FSRS считается «в
   тени» на каждом ревью и пишется в БД, но не используется для
   due-очереди/статистики. Это позволяет накопить реальную историю
   FSRS-состояния карточек ДО включения флага — когда флаг включат,
   карточки не стартуют с нуля.
2. **Локальная/staging проверка:** задать `FSRS_ENABLED=true` в
   `.env.local`, вручную пройти сценарий из `fsrs-test-report.md`
   (разбор по всем 4 кнопкам, due-очередь, статистика, старая и
   новая карточка).
3. **Прод:** включать `FSRS_ENABLED=true` в переменных окружения
   Vercel — **только по отдельному подтверждению владельца проекта**,
   не автоматически в рамках этой фазы (см. финальный запрет
   задания — миграция БД тоже не применялась к продакшену).
4. Ограниченный rollout по пользователям (A/B по `owner_id`, процент
   аудитории) не реализован в этой фазе — флаг сейчас глобальный
   (on/off для всего приложения разом). Если понадобится постепенный
   rollout по пользователям — расширить `isFsrsEnabled()` до
   принятия `ownerId` и собственной таблицы/hash-разбиения, не меняя
   сигнатуру вызова в `reviewWord` кардинально.

## Rollback

Откат — это просто возврат `FSRS_ENABLED` в `false` (или удаление
переменной). Ничего в БД откатывать не нужно:

- Пока флаг был включён, `reviewWord` **продолжал обновлять** legacy
  SM-2 поля (`ease_factor`/`interval_days`/`repetitions`) на каждом
  ревью — они не «застыли» на момент включения флага. После отката
  SM-2 продолжает планирование с того состояния, в котором он был бы,
  если бы FSRS вообще не включали.
- Данные FSRS (`fsrs_*` колонки, `review_log.previous_state_json`/
  `next_state_json`) никуда не делись — можно включить флаг снова
  позже без потери истории.
- Сама миграция `0032_fsrs_state.sql` — additive, откатывать её не
  требуется даже при полном отказе от FSRS; в крайнем случае
  (отдельное решение, не часть этой фазы) можно `drop column` новые
  поля, ничего в существующем поведении SM-2 от этого не изменится.

## Что требует отдельного подтверждения перед production

1. **Применение миграции `0032_fsrs_state.sql` к продакшен-БД** — не
   выполнялось, только локально (см. `fsrs-test-report.md`).
2. **Установка `FSRS_ENABLED=true` в проде** — отдельное решение
   после того, как миграция БД применена и алгоритм проверен на
   реальных пользователях достаточное время в shadow-режиме
   (собранная история `fsrs_*`/`review_log.next_state_json` может
   быть просмотрена до включения флага, чтобы сравнить, какие
   интервалы предложил бы FSRS, ничего не меняя для пользователей).
3. Решение о судьбе неиспользуемых при FSRS SM-2-настроек в Study
   Settings (`easy_bonus`, `interval_modifier` и т.д.) — оставить как
   есть (действуют только в режиме `FSRS_ENABLED=false`) или
   скорректировать UI/копирайт, чтобы не вводить пользователя в
   заблуждение, если он их поменяет, а флаг уже включён. Не решалось
   в этой фазе намеренно (правило «не меняй UI без необходимости»).
