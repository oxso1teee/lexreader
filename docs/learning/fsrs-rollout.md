# M2 Learning Upgrade — feature flags, rollout, rollback

> **Обновлено в FSRS Schema Compatibility Hotfix** (2026-08-01, после
> production-инцидента — см. `fsrs-production-rollout-phase-1.md`):
> флаг стал не одним, а двумя. Раздел ниже описывает актуальную модель;
> подробный разбор причины и устройства — в
> `fsrs-schema-compatibility.md`.

## Два флага, не один

`src/lib/fsrs-flags.ts` (`getFsrsFlags()`) — единственное место, где
комбинируются оба флага:

```ts
export interface FsrsFlags {
  schemaReady: boolean;   // migration 0032 подтверждённо применена
  enabled: boolean;       // FSRS авторитетен для due_at
  shadowEnabled: boolean; // можно читать/писать fsrs_*-поля
}
```

- **`FSRS_SCHEMA_READY`** — подтверждение, что колонки `fsrs_*` и
  `review_log.scheduler_type`/`previous_state_json`/`next_state_json`
  реально существуют в текущей БД. `false`/не задана → они вообще не
  запрашиваются и не пишутся (безопасно даже против БД без миграции).
- **`FSRS_ENABLED`** — кого считать авторитетным для `due_at`. Работает
  только вместе с `FSRS_SCHEMA_READY=true`:
  `enabled = schemaReady && FSRS_ENABLED === "true"`. Включение
  `FSRS_ENABLED=true` без подтверждённой миграции **не является
  опасной конфигурацией** — она просто игнорируется, легаси остаётся
  авторитетным, в лог пишется диагностическое предупреждение без
  приватных данных.

Оба — server-side переменные (НЕ `NEXT_PUBLIC_*`), недоступны клиенту
напрямую.

## Почему это не «клиентский флаг как единственная защита»

`getFsrsFlags()` вызывается только из серверного кода:

- `src/app/(app)/brain/[deckId]/review/actions.ts` (`reviewWord`) —
  единственное место, где флаги решают, какой `due_at` реально
  запишется в БД, и какие колонки вообще участвуют в select/update/
  insert. Это server action, клиент не может передать сюда собственное
  значение — функция ничего не принимает параметром извне для этого.
- `src/app/(app)/brain/[deckId]/review/page.tsx` — server component,
  вычисляет флаги один раз при рендере страницы и передаёт вниз
  `flags.enabled` как обычный React-проп в `ReviewModeSwitcher` →
  `ReviewSession`.

Клиентский компонент (`review-session.tsx`) получает уже готовое
значение только для одной цели — выбрать, чьей формулой посчитать
**предпросмотр** интервала на кнопках оценки (косметика, ничего не
сохраняет). Даже если бы кто-то подделал этот проп через devtools,
реальное сохранение оценки всё равно идёт через `reviewWord`,
которая не доверяет клиенту и проверяет оба флага заново на сервере.

## Rollout (четыре фазы, см. `fsrs-schema-compatibility.md` за подробностями)

- **Phase A (текущее состояние production):** оба флага не заданы.
  Код уже деплоится безопасно даже против БД без миграции 0032 —
  fsrs_*-колонки/scheduler_type вообще не запрашиваются и не пишутся,
  review работает полностью на легаси-схеме.
- **Phase B:** ручной backup production-БД, затем применение
  `0032_fsrs_state.sql` — **не выполнено в этой фазе**, требует
  отдельного подтверждения владельца (см. "Что требует отдельного
  подтверждения" ниже — прежде всего backup/PITR).
- **Phase C:** `FSRS_SCHEMA_READY=true`, `FSRS_ENABLED` остаётся
  `false`/не задан — shadow-режим: FSRS считается и пишется на каждом
  ревью, `due_at` остаётся legacy. Позволяет накопить реальную историю
  FSRS-состояния карточек ДО включения `FSRS_ENABLED` — когда его
  включат, карточки не стартуют с нуля.
- **Phase D:** `FSRS_ENABLED=true` (при уже `FSRS_SCHEMA_READY=true`)
  — **только по отдельному подтверждению владельца проекта**, после
  периода наблюдения за shadow-данными.

Ограниченный rollout по пользователям (A/B по `owner_id`, процент
аудитории) не реализован ни в одной из фаз — оба флага сейчас
глобальные (on/off для всего приложения разом). Если понадобится
постепенный rollout по пользователям — расширить `getFsrsFlags()` до
принятия `ownerId` и собственной таблицы/hash-разбиения, не меняя
сигнатуру вызова в `reviewWord` кардинально.

## Rollback

Откат — это просто возврат `FSRS_ENABLED` в `false` (или удаление
переменной) — `FSRS_SCHEMA_READY` можно оставить как есть, шаг назад
не требуется. Ничего в БД откатывать не нужно:

- Пока `FSRS_ENABLED` был включён, `reviewWord` **продолжал
  обновлять** legacy SM-2 поля (`ease_factor`/`interval_days`/
  `repetitions`) на каждом ревью — они не «застыли» на момент
  включения флага. После отката SM-2 продолжает планирование с того
  состояния, в котором он был бы, если бы FSRS вообще не включали.
- Данные FSRS (`fsrs_*` колонки, `review_log.previous_state_json`/
  `next_state_json`) никуда не делись — можно включить флаг снова
  позже без потери истории.
- Сама миграция `0032_fsrs_state.sql` — additive, откатывать её не
  требуется даже при полном отказе от FSRS; в крайнем случае
  (отдельное решение, не часть этой фазы) можно `drop column` новые
  поля, ничего в существующем поведении SM-2 от этого не изменится.
- Если проблема обнаружена ДО применения миграции (Phase A) — откат
  ещё проще: код уже безопасен против легаси-схемы, `FSRS_SCHEMA_READY`
  просто не выставляется, ничего дополнительно откатывать не нужно.

## Что требует отдельного подтверждения перед production

1. **Backup/PITR для production Supabase** — на момент этой фазы
   подтверждённо отсутствуют (Free-план, см.
   `fsrs-production-rollout-phase-1.md`). Блокирует применение
   миграции 0032, пока не решено (апгрейд плана или ручной снимок).
2. **Применение миграции `0032_fsrs_state.sql` к продакшен-БД** — не
   выполнялось, только локально (см. `fsrs-test-report.md`,
   `fsrs-schema-compatibility.md`).
3. **Установка `FSRS_SCHEMA_READY=true` в проде** — только сразу после
   (2), в одном контролируемом окне.
4. **Установка `FSRS_ENABLED=true` в проде** — отдельное решение
   после того, как миграция БД применена и алгоритм проверен на
   реальных пользователях достаточное время в shadow-режиме
   (собранная история `fsrs_*`/`review_log.next_state_json` может
   быть просмотрена до включения флага, чтобы сравнить, какие
   интервалы предложил бы FSRS, ничего не меняя для пользователей).
5. Решение о судьбе неиспользуемых при FSRS SM-2-настроек в Study
   Settings (`easy_bonus`, `interval_modifier` и т.д.) — оставить как
   есть (действуют только в режиме `FSRS_ENABLED=false`) или
   скорректировать UI/копирайт, чтобы не вводить пользователя в
   заблуждение, если он их поменяет, а флаг уже включён. Не решалось
   в этой фазе намеренно (правило «не меняй UI без необходимости»).
